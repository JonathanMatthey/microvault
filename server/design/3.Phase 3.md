# Phase 3 — Web Monetization via Open Payments

## Purpose
Introduce Web Monetization and Open Payments so users stream micropayments while browsing the client, and the backend automatically tracks and credits payments as they accumulate. Phase 3 connects the existing credit system to an Interledger/Web Monetization flow via Open Payments incoming-payment objects and keeps uploads/downloads/storage accounting unchanged.

## Goals
- Backend exposes monetization configuration (payment pointer, asset code/scale, units-per-credit conversion).
- Frontend injects Web Monetization `<link rel="monetization">` tag and listens for spec events.
- Frontend notifies backend of incoming-payment URLs when payment events occur (user logged in).
- Backend fetches incoming-payment state, creates persistent PaymentRecord entries, and starts background polling each active payment every 30 seconds.
- As incoming-payment value increases over time (more micropayments streamed), backend credits the user with deltas every poll cycle.
- Incoming payments go inactive after 24 hours of no value increase; reactivate on fresh event.
- Preserve resumable uploads and existing auth (Google SSO) with no regressions to Phase 2 functionality.

## Non-Goals
- Billing for storage snapshots (already defined; no change to cadence).
- Egress/download implementation details beyond charging rules (handled separately).
- S3 migration or encryption (future phases).
- Multi-tenant wallets or per-user payment pointers.
- Receipt signature verification (stub for now; TODO for hardening).

## Architecture
### Backend
- **Config**: Monetization block with `payment_pointer`, `incoming_auth_token` (optional), `units_per_credit`, `min_topup_units`, `max_topup_units`, `enabled` flag.
- **Wallet discovery**: On startup, fetch wallet address JSON from payment pointer; extract and validate `assetCode` and `assetScale` (no static config needed).
- **Repository**: Persistent store for incoming-payment tracking (Redis in prod, memory in tests).
  - Per incoming-payment URL: `userID`, `assetCode`, `assetScale`, `lastValue` (minor units), `createdAt`, `lastUpdatedAt`, `lastChangeAt`, `active` flag.
- **Endpoint**: `GET /monetization/config` (auth not required) returns payment pointer, derived asset code/scale, units_per_credit, min/max amounts, enabled flag.
- **Endpoint**: `POST /monetization/verify` (auth required) accepts `{incoming_payment: url}`, fetches the URL once, stores/updates PaymentRecord, credits any immediate delta, returns status.
- **Poller**: Background goroutine scans all active PaymentRecords every 30 seconds:
  - Fetch latest state for each URL.
  - Compute delta vs. last stored value.
  - If delta > 0: credit the user and update record.
  - If no change for 24 hours: mark record inactive.
- **Ledger**: Reuse existing ledger (Redis in prod, memory in tests). No pricing changes.
- **Auth**: Uses existing Google ID token for `/monetization/verify`. No devlogin in prod builds.

### Frontend
- On load, inject `<link rel="monetization" href="<payment-pointer-url>">` into `<head>`.
- Fetch `/monetization/config` to verify monetization is enabled and get rates.
- Listen for Web Monetization spec `monetization` events on the link element.
- On event, POST the `incomingPayment` URL to `/monetization/verify` with Bearer token.
- Show current balance and refresh after verify response; keep existing upload/resume UX.
- If monetization disabled in config, skip link injection and event wiring.

## Flows
1) **Config fetch**: Client GET `/monetization/config` → receives payment pointer + derived asset + conversion rate.
2) **Link injection**: Client injects monetization link; browser obtains grant from Web Monetization provider.
3) **Incoming payment created**: Provider creates incoming-payment URL on the backend wallet.
4) **Monetization event**: Browser fires `monetization` event with `incomingPayment` URL in detail.
5) **Verify & track**: Client POST `/monetization/verify` with URL → backend fetches, creates/updates PaymentRecord, credits delta, returns status.
6) **Background polling**: Every 30s, poller fetches all active incoming-payment URLs, computes new deltas, credits user, marks stale payments inactive.
7) **Reactivation**: If user sends new incoming-payment event for an inactive payment, it reactivates and polling resumes.

## Data Contracts
- **GET /monetization/config** (200):
```json
{
  "enabled": true,
  "payment_pointer": "$ilp.example.com/user/alice",
  "asset_code": "USD",
  "asset_scale": 2,
  "units_per_credit": 100,
  "min_topup_units": 0,
  "max_topup_units": 1000000
}
```
- **POST /monetization/verify** (auth required):
Request:
```json
{
  "incoming_payment": "https://ilp.example.com/incoming-payments/ip-123"
}
```
Response (200):
```json
{
  "message": "incoming payment recorded",
  "delta_units": 50,
  "credited": 5000,           // credited in CreditUnit (scale 4)
  "credits": 25000,           // new balance
  "incomingPayment": "https://ilp.example.com/incoming-payments/ip-123"
}
```
Error: 400 on bad/unallowed URL; 401 on missing/invalid auth; 404 if monetization disabled.

- **Incoming-payment object** (fetched by poller):
```json
{
  "receivedAmount": {
    "value": "500",           // current accumulated minor units
    "assetCode": "USD",
    "assetScale": 2
  },
  "authServer": "https://...",
  "id": "ip-123"
}
```

## Pricing & Conversion
- Existing credit scale: `CREDIT_SCALE = 4`, `1 credit = 10_000 units`.
- Config parameter: `units_per_credit` = wallet currency minor units per **one credit** (e.g., 100 USD cents = 1 credit).
- Conversion:
```
credited_units = (delta_minor_units * CreditUnit) / units_per_credit
```
- Asset code/scale: Derived from wallet address JSON at startup; validated against each incoming-payment fetch.

## Persistence & State Management
- **PaymentRecord**: Stored in repository (Redis/memory) with:
  - `url`: incoming-payment URL (key).
  - `userId`: user who initiated the payment.
  - `assetCode`, `assetScale`: validation fields.
  - `lastValue`: last observed `receivedAmount.value`.
  - `createdAt`: when record was first created.
  - `lastUpdatedAt`: when record was last touched.
  - `lastChangeAt`: when `lastValue` last increased; used to detect 24h inactivity.
  - `active`: boolean; false if marked inactive due to 24h no-change.
- **Lifecycle**:
  - On first POST `/monetization/verify` for a URL → create PaymentRecord, fetch, credit delta, add to active set.
  - Every 30s poller tick → fetch all active, compute deltas, credit, update `lastUpdatedAt`/`lastChangeAt`.
  - After 24h without value increase → mark inactive, remove from active set.
  - Next POST for inactive URL → reactivate (set `active=true`, re-add to active set), resume polling.

## Testing
- **Unit**: Memory repo validates create/update/reactivate; poller mocks HTTP server simulating increasing values, asserts credits issued.
- **Integration**: Redis repo CRUD; poller scanning mock redis store; multiple active payments.
- **E2E (manual)**: enable monetization config, load client, inject Web Monetization link, confirm monetization events fire, verify `/monetization/verify` POSTs, check ledger balance increments via logs.

## Rollout
- Feature-flag monetization via config (`monetization.enabled`).
- If disabled, `/monetization/config` returns `enabled:false` and frontend skips event wiring.
- Poller only runs if monetization enabled.
- At startup, attempt wallet asset derivation; log warning if failed, but proceed with config defaults if available.

## Risks & Mitigations
- **Fetch failures**: Poller logs errors but continues scanning other URLs; consider exponential backoff in Phase 3.1.
- **Network latency**: Poller timeout set to 10s; individual fetch timeout 5s. Transient failures are retried next cycle.
- **Double-credit**: Currently none (no idempotency key on receipts); implement `request_id` tracking for `/monetization/verify` POSTs in Phase 3.1.
- **Reactivation abuse**: Attacker could repeatedly POST inactive payments; rate-limit POSTs per user/IP in Phase 3.1.
- **Asset mismatch**: Reject if incoming-payment asset_code/scale differ from derived wallet values.
- **SSRF**: Restrict incoming-payment URLs to wallet host (already checked).

## Success Criteria
- Monetization config served to clients with derived asset code/scale.
- Frontend injects link, listens for events, POSTs incoming-payment URLs.
- `/monetization/verify` endpoint persists payments, credits immediate deltas.
- Poller scans all active payments every 30s, credits new deltas, marks stale payments inactive.
- Payments reactivate on fresh events; balance increments as value accumulates over time.
- All Phase 2 functionality (auth, uploads, credit deduction) remains intact.
