# Phase 1 — Identity, Accounting, and Policy Engine

## Purpose

Phase 1 establishes the **financial and identity core** of the system.  
No file storage, no bytes, and no external dependencies are introduced.

The outcome of this phase is confidence that:
- identity is correct and stable,
- credit accounting is exact and deterministic,
- account state transitions are correct,
- and all business rules are enforced **purely through tests**.

Nothing in later phases is allowed to bypass or reimplement this logic.

---

## Goals

By the end of Phase 1:

- A developer can run the system **entirely locally**
- Multiple users can log in (real OIDC or dev-login)
- Credits can be added, deducted, and go negative safely
- Account freeze/unfreeze behavior is deterministic
- All logic is validated through **test-driven development**

---

## Non-Goals (Explicitly Out of Scope)

- File uploads or downloads
- S3 or any storage backend
- tus or chunking
- Filesystem semantics
- Encryption
- Background schedulers

Phase 1 must remain **small, fast, and testable**.

---

## Core Concepts

### User Identity

- Users authenticate via **OIDC**
- Each authenticated user yields a stable `UserID`
- A deterministic `userHash` is derived from `UserID`
- `userHash` generation must be:
  - stable across restarts
  - deterministic
  - collision-resistant

> No persistence layer is required yet, but interfaces must allow it later.

---

### Credit System

#### Fixed-Point Representation

- All credits are stored as **signed int64**
- A fixed decimal scale is applied

```text
CREDIT_SCALE = 4
1 credit = 10_000 internal units
```

Rules:
- No floating point math anywhere in the accounting layer
- Overflow and underflow must be tested

---

### Account Balance

- Balances may go **negative**
- Negative balance does **not** block in-flight operations
- Negative balance affects **future authorization decisions**

Account state is derived, not stored:

```text
balance >= 0 → Active
balance <  0 → Frozen
```

---

### Activity Tracking

- Any **successful login** updates `last_active_at`
- Used later for retention enforcement
- No other operation counts as activity in v1

---

## Policy Engine

The policy engine answers questions — it does **not** mutate state.

Required decisions:

- `CanUpload(user)`
- `CanDownload(user)`
- `IsFrozen(user)`

Rules:

- Upload allowed only if:
  - account is not frozen
  - balance >= minimum required for one ingress chunk (constant)
- Download allowed only if:
  - account is not frozen
- Listing and metadata access always allowed

The policy engine must be:
- pure
- deterministic
- exhaustively tested

## Interfaces

### Accounting Interface

```go
type Ledger interface {
    Balance(userID string) int64
    Credit(userID string, amount int64) error
    Debit(userID string, amount int64) error
}
```

Phase 1 implementation:
- in-memory only
- concurrency-safe

Future implementations:
- TigerBeetle
- persistent store

---

### Identity Interface

```go
type IdentityProvider interface {
    Authenticate(ctx context.Context) (User, error)
}
```

Implementations:
- OIDC provider (prod)
- Dev-login provider (build-tagged)

## Test-Driven Development Requirements

### Mandatory Test Categories

1. **Credit Arithmetic**
   - scaling correctness
   - rounding
   - negative balances
   - overflow protection

2. **Ledger Behavior**
   - concurrent debits
   - idempotency assumptions
   - consistency under load

3. **Policy Decisions**
   - upload allowed / denied
   - download allowed / denied
   - freeze transitions

4. **Identity Stability**
   - same user → same hash
   - different users → different hashes

5. **Activity Tracking**
   - login updates timestamp
   - failed login does not

---

## Local Development Requirements

- No external services required
- Dev-login enabled via Go build tag:
  - e.g. `-tags=devlogin`
- Ability to simulate:
  - multiple users
  - arbitrary balances
  - freeze/unfreeze transitions

---

## Success Criteria (Exit Conditions)

Phase 1 is considered **complete** when:

- ✅ `go test ./...` passes with high coverage
- ✅ No production code depends on storage or networking side effects
- ✅ All policy rules are proven via tests
- ✅ Balances are never stored as floats
- ✅ Account state is always derivable from balance
- ✅ A developer can manually simulate real user scenarios locally

If any later phase requires modifying Phase 1 logic, Phase 1 was not finished correctly.

---

## Guiding Principle

> **If the money logic is wrong, nothing else matters.**

Phase 1 must be boring, precise, and extremely well tested.
