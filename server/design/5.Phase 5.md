# Phase 5 — S3 Storage Migration (Remove TUS, Filesystem, Add Presigned URLs)

## Purpose

Phase 5 **completely replaces** the TUS upload protocol and local filesystem storage with **S3-compatible object storage** using presigned URLs. This simplifies the architecture, improves scalability, and eliminates the complexity of TUS protocol management and `.info` file parsing.

All developers (local and production) will use **Hetzner Object Storage** as the backend. There is no local filesystem fallback—S3 is required for all environments.

The outcome of this phase is:
- TUS protocol and tusd library completely removed from backend
- Local filesystem storage removed (no more `data/` directory)
- All uploads/downloads use S3 presigned URLs
- Clients upload directly to S3 (no proxy through server)
- Downloads stream directly from S3 (or via redirect)
- All metadata stored in Redis (no more `.info` files)
- Path-based isolation prevents cross-user file access
- Simplified client code (native fetch/XHR, no tus-js-client)
- Faster uploads/downloads (direct S3, no server bottleneck)

### 2. Storage Layout in S3

**Path structure:**
```
s3://h32bb/
  users/
    {userHash1}/
      {uploadID1}
      {uploadID2}
    {userHash2}/
      {uploadID3}
```

**Key properties:**
- `userHash` = SHA256 hex of user ID (same as Phase 1-4)
- `uploadID` = UUID v4 generated by server
- No `.info` files (metadata in Redis)
- No directory objects (S3 uses key prefixes)

**Example S3 key:**
```
users/590cedf34d6265784e6f720e4fa4351f5e2c5c4047d3046135dda88ea02b93c7/a1b2c3d4-e5f6-7890-abcd-ef1234567890
```

**Isolation guarantee:**
- Presigned URLs are scoped to exact S3 key
- User A cannot access User B's files (different key prefix)
- Signature validation prevents path tampering

### 3. Backend Upload Flow (Presigned PUT URLs)

**Endpoint: `POST /files/upload-url` (auth required)**

Generates a presigned S3 PUT URL for direct client upload.

**Request:**
```json
{
  "filename": "document.pdf",
  "size": 5242880,
  "contentType": "application/pdf"
}
```

**Pre-upload checks:**
1. Extract user ID from authentication.
2. Query ledger for current balance.
3. Check policy: `CanUpload(balance)` → must not be frozen.
4. Calculate ingress cost: `CalculateIngressCost(size)`.
5. If frozen or insufficient balance → reject with 402 Payment Required.
6. If allowed → proceed to generate presigned URL.

**Server actions:**
1. Generate new `uploadID` (UUID v4).
2. Construct S3 key: `users/{userHash}/{uploadID}`.
3. Generate presigned PUT URL (valid for 1 hour).
4. Deduct ingress credits immediately (no chunking, full file charged upfront).
5. Store metadata in Redis:
   - `file:{uploadID}` hash: `{userId, filename, size, contentType, createdAt, status: pending}`
   - `user:{userId}:files` sorted set: `{uploadID: timestamp}`
6. Return presigned URL and uploadID to client.

**Response (200):**
```json
{
  "uploadId": "a1b2c3d4-e5f6-7890-abcd-ef1234567890",
  "uploadUrl": "https://hel1.your-objectstorage.com/h32bb/users/590cedf.../a1b2c3d4...?X-Amz-Algorithm=AWS4-HMAC-SHA256&X-Amz-Credential=...&X-Amz-Date=...&X-Amz-Expires=3600&X-Amz-Signature=...",
  "expiresIn": 3600,
  "cost": 156
}
```

**Error responses:**
- 402: Frozen or insufficient balance.
- 401: Missing or invalid authentication.
- 400: Missing or invalid request body.

### 4. Client Upload Flow (Direct to S3)

**Frontend implementation:**

```javascript
// 1. Request presigned URL from server
const response = await fetch('/files/upload-url', {
  method: 'POST',
  headers: {
    'Authorization': `Bearer ${token}`,
    'Content-Type': 'application/json'
  },
  body: JSON.stringify({
    filename: file.name,
    size: file.size,
    contentType: file.type
  })
});

const { uploadId, uploadUrl, expiresIn, cost } = await response.json();

// 2. Upload directly to S3 using presigned URL
const uploadResponse = await fetch(uploadUrl, {
  method: 'PUT',
  body: file,
  headers: {
    'Content-Type': file.type
  }
});

if (uploadResponse.ok) {
  // 3. Mark upload complete on server
  await fetch(`/files/${uploadId}/complete`, {
    method: 'POST',
    headers: { 'Authorization': `Bearer ${token}` }
  });
  console.log('Upload complete!');
} else {
  console.error('Upload failed:', uploadResponse.statusText);
}
```

**Progress tracking (optional):**
```javascript
const xhr = new XMLHttpRequest();
xhr.upload.addEventListener('progress', (e) => {
  if (e.lengthComputable) {
    const percent = (e.loaded / e.total) * 100;
    updateProgressBar(percent);
  }
});
xhr.open('PUT', uploadUrl);
xhr.setRequestHeader('Content-Type', file.type);
xhr.send(file);
```

**Advantages over TUS:**
- ✅ Simpler client code (native fetch, no library)
- ✅ Faster uploads (direct to S3, no proxy)
- ✅ No chunking complexity
- ✅ No resumable upload protocol overhead
- ✅ Browser handles all upload mechanics

### 5. Upload Completion Endpoint

**Endpoint: `POST /files/{uploadId}/complete` (auth required)**

Marks upload as complete and updates metadata.

**Server actions:**
1. Verify uploadID belongs to authenticated user (check Redis).
2. Optionally verify S3 object exists (HEAD request).
3. Update Redis metadata: set `status: complete`, `uploadedAt: now()`.
4. Add to Redis index for listing.

**Response (200):**
```json
{
  "message": "upload complete",
  "uploadId": "a1b2c3d4-e5f6-7890-abcd-ef1234567890",
  "filename": "document.pdf",
  "size": 5242880
}
```

**Error responses:**
- 404: Upload ID not found or belongs to different user.
- 401: Missing or invalid authentication.

**Note:** This step is separate from presigned URL generation to handle:
- Upload abandonment (user never completes)
- Upload failures (client error, network issue)
- Status tracking for incomplete uploads

### 6. Backend Download Flow (Presigned GET URLs)

**Endpoint: `GET /files/{uploadId}/download` (auth required)**

Generates a presigned S3 GET URL and redirects client (or returns URL).

**Pre-download checks:**
1. Extract user ID from authentication.
2. Query ledger for current balance.
3. Check policy: `CanDownload(balance)` → must not be frozen.
4. Verify uploadID belongs to this user (check Redis metadata).
5. If frozen → reject with 402 Payment Required.
6. If file not found or wrong user → reject with 404.
7. If allowed → proceed.

**Server actions:**
1. Fetch file metadata from Redis (size, filename).
2. Calculate egress cost: `CalculateEgressCost(size)`.
3. Deduct egress credits immediately (full file charged upfront).
4. Construct S3 key: `users/{userHash}/{uploadID}`.
5. Generate presigned GET URL (valid for 5 minutes).
6. Return 302 redirect to presigned URL (or JSON with URL).

**Response (302 Redirect):**
```
Location: https://hel1.your-objectstorage.com/h32bb/users/590cedf.../a1b2c3d4...?X-Amz-Algorithm=...&X-Amz-Signature=...
```

**Or Response (200 JSON):**
```json
{
  "downloadUrl": "https://hel1.your-objectstorage.com/h32bb/users/590cedf.../a1b2c3d4...?X-Amz-Algorithm=...&X-Amz-Signature=...",
  "expiresIn": 300,
  "filename": "document.pdf",
  "size": 5242880,
  "cost": 1250
}
```

**Client downloads directly from presigned URL** (browser or fetch).

**Error responses:**
- 402: Frozen or insufficient balance.
- 404: Upload ID not found or belongs to different user.
- 401: Missing or invalid authentication.

### 7. Backend File Listing (No Changes)

**Endpoint: `GET /files` (auth required)**

Lists files from Redis index (no S3 interaction).

**Implementation:**
- Query Redis: `ZREVRANGE user:{userId}:files 0 -1` (sorted by timestamp).
- For each uploadID, fetch metadata: `HGETALL file:{uploadID}`.
- Filter to only `status: complete`.
- Calculate estimated download cost per file.
- Return JSON array.

**No changes from Phase 4** (already Redis-backed).

---

### 8. Backend File Deletion

**Endpoint: `DELETE /files/{uploadId}` (auth required)**

Deletes file from S3 and removes metadata from Redis.

**Server actions:**
1. Verify uploadID belongs to authenticated user (check Redis).
2. Construct S3 key: `users/{userHash}/{uploadID}`.
3. Delete S3 object: `s3.DeleteObject(bucket, key)`.
4. Remove from Redis:
   - `DEL file:{uploadID}`
   - `ZREM user:{userId}:files {uploadID}`
5. Log deletion for audit.

**Response (200):**
```json
{
  "message": "file deleted",
  "uploadId": "a1b2c3d4-e5f6-7890-abcd-ef1234567890",
  "freedBytes": 5242880
}
```

**Error responses:**
- 404: Upload ID not found or belongs to different user.
- 401: Missing or invalid authentication.
- 500: S3 deletion failed.

### 9. Credit Charging Changes

**Upload (Ingress):**
- **OLD (Phase 2-4):** Charged per 16 MiB chunk after successful write.
- **NEW (Phase 5):** Charged upfront when presigned URL is generated (full file cost).
- **Rationale:** No server involvement in upload, can't track chunks. Simpler accounting.
- **Formula:** `cost = CalculateIngressCost(fileSize)` (unchanged).

**Download (Egress):**
- **OLD (Phase 4):** Charged per 16 MiB chunk as streamed through server.
- **NEW (Phase 5):** Charged upfront when presigned URL is generated (full file cost).
- **Rationale:** Download is direct from S3, server can't track chunks. Simpler accounting.
- **Formula:** `cost = CalculateEgressCost(fileSize)` (unchanged).

**Trade-off:**
- ❌ User charged even if upload/download fails partway.
- ✅ Simpler server code (no chunking logic).
- ✅ Presigned URL expiry limits abandoned uploads.
- ✅ Can refund failed uploads in Phase 5.1 if needed (check S3 object existence).

### 10. Redis Metadata Schema

**File metadata (hash):**
```
Key: file:{uploadID}

Fields:
  userId: <user-id>
  filename: <original-filename>
  size: <bytes>
  contentType: <mime-type>
  createdAt: <RFC3339-timestamp>
  uploadedAt: <RFC3339-timestamp> (set on /complete)
  status: pending|complete
  s3Key: users/{userHash}/{uploadID}
```

**User file index (sorted set):**
```
Key: user:{userId}:files

Members: {uploadID}
Scores: {unix-timestamp} (for sorting newest first)
```

**Listing query:**
```redis
ZREVRANGE user:{userId}:files 0 -1
→ [uploadID1, uploadID2, uploadID3]

HGETALL file:{uploadID1}
→ {userId: ..., filename: ..., size: ..., ...}
```

- **Then** the request must fail with 402 Payment Required

- **And** no credits are deducted

- **Then** S3 object must be deleted
- **And** Redis metadata must be removed
- **And** no charge occurs

- **Given** two users with different uploads
- **When** User A attempts to download User B's file
- **Then** the request must fail with 404

- **Given** a user marks upload as complete
- **When** calling POST `/files/{uploadID}/complete`
- **Then** server verifies S3 object exists (HEAD request)

## Security Considerations

### Presigned URL Security

- ✅ URLs contain cryptographic signature (HMAC-SHA256)
- ✅ Tampering invalidates signature
- ✅ Time-limited expiry (1 hour upload, 5 min download)
- ✅ Scoped to exact S3 key (cannot access other files)
- ✅ Action-limited (PUT or GET, not both)

### Cross-User Isolation

- ✅ Server enforces userID → uploadID ownership via Redis

## Risks & Mitigations

### Risk: Presigned URL Expiry

**Problem:** User requests upload URL but takes > 1 hour to upload.

**Mitigation:**
- Set generous expiry (1 hour default).
- Frontend warns if upload not started within time.
- User can re-request presigned URL (generates new uploadID).
- Consider S3 multipart uploads in Phase 5.1 for large files.

### Risk: Abandoned Uploads

**Problem:** User gets presigned URL but never uploads to S3.

**Mitigation:**
- Mark upload `status: pending` in Redis.
- Background job cleans up pending uploads > 24 hours old.
- Remove Redis metadata if S3 object doesn't exist.
- Consider refunding credits in Phase 5.1 if needed.

### Risk: S3 Outage

**Problem:** Hetzner S3 unavailable, users cannot upload/download.

**Mitigation:**
- S3 is single point of failure (same as filesystem in Phase 4).
- Use Hetzner status page for monitoring.
- Consider multi-region or backup bucket in Phase 6 if needed.
- Presigned URL generation fails fast (return 503).

### Risk: CORS Misconfiguration

**Problem:** Browser blocks uploads due to missing CORS headers.

**Mitigation:**
- Test CORS configuration in staging before production.
- Include `localhost` in CORS for local development.
- Use browser DevTools to debug CORS errors.
- Hetzner Object Storage has CORS UI for easy config.

## Notes

### Critical Breaking Changes

- **Phase 5 is incompatible with Phase 4 data (fresh start required)**
- **ALL local filesystem storage is removed** — no fallback, no exception handling, no conditional logic
- **The `./data/` directory must not exist** in any environment (dev, staging, prod)
- **Every developer must link an S3 bucket** for local work (no local-only development)
- **Filesystem code paths are completely removed** — grep should find zero `os.Open`, `os.Create`, etc. related to uploads
- **TUS protocol is completely removed** — no tusd binary, no tusd Go bindings

### Architectural Decisions

- ✅ **No fallback:** Filesystem storage is completely removed.
- ✅ **S3 is mandatory:** Even for local development.
- ✅ **Same code everywhere:** Dev and prod use identical code paths.
- ✅ **CORS is critical:** Test thoroughly in staging before production.
- ✅ **Charging upfront:** Simpler accounting but charges even if upload/download fails partway.
- ✅ **Hetzner credentials:** Store securely, use env vars or secrets manager in prod (never hardcode).
- ✅ **Path isolation:** `users/{userHash}/` prevents cross-user access via S3 key scoping.
- ✅ **Presigned URLs:** Time-limited, action-limited, path-limited (secure by design).
