# Long-Term File Storage Service — v1 Specification

## Overview

This project provides a **Go-based web application** for long-term file and data storage.  
It exposes a **filesystem-like interface** to authenticated users and charges usage via **Interledger Web Monetization** credits.

### Frontend behavior (current)

- File uploads start automatically when selected; subsequent selections are queued and displayed in an on-page queue, with the active upload highlighted.
- A single cancel control aborts the active upload and advances to the next queued item.
- The client polls `/user` every 10s to keep the displayed credit balance current.

Authentication and authorization are handled by the Go application to allow:
- deterministic accounting,
- future cryptographic processing,
- and flexible backend storage.

**Phase 2-4**: Backend uses local filesystem storage in `./data/` directory.

**Phase 5+**: Backend uses **S3-compatible object storage** (Hetzner). Uploads are proxied through the backend to S3 (no CORS issues in dev) and stored as `users/{userHash}/{uploadId}-{filename}`. Downloads use presigned URLs resolved by `uploadId`. We keep a server-side proxy path available because Hetzner S3 cannot be given custom CSP headers; proxying keeps the browser compliant while still leveraging Hetzner as storage. The server handles authentication, authorization, and accounting.

This specification describes the complete v1 system. Implementation follows a phased approach:

- **Phase 1**: Identity, accounting core, policy engine (✅ Complete)
- **Phase 2**: TUS upload integration with credit deduction (✅ Complete)
- **Phase 3**: Web Monetization payment integration (✅ Complete)
- **Phase 4**: Download, listing, and egress charging (✅ Complete)
- **Phase 5**: S3 storage migration, proxy uploads & presigned downloads (current)
- **Phase 6**: Sharing links (planned)
- **Phase 7**: CDN integration and encryption (Future)

Each phase maintains backward compatibility and testability.

## Authentication & Identity

- Users authenticate via **OIDC** in production, initially using **Google SSO** (Phase 4+).
- Each authenticated user is assigned a stable **user identity**.
- A **dev-login mode** is provided for local development (Phase 1+):
  - Allows logging in as arbitrary email identities via `X-User-ID` header.
  - Enabled only via **Go build tags** (must not be compiled into production builds).
  - Used for testing all features without external dependencies.

## Credit & Pricing Model

### Credit System

- Credits are the internal accounting unit.
- Credit calculations use **signed 64-bit integers** with fixed-point scaling.

```text
CREDIT_SCALE = 4
INTERNAL_UNIT = 10^CREDIT_SCALE = 10_000 (derived)
UNITS_PER_CREDIT = minor currency units required for 1 credit (from config)

credited_raw = (received_minor / UNITS_PER_CREDIT) * INTERNAL_UNIT
displayed_credits = credited_raw / INTERNAL_UNIT

Examples:
- Wallet scale=2 (cents), UNITS_PER_CREDIT=10, receive $1.23 = 123 minor
  credited_raw = (123 / 10) * 10_000 = 123_000 → displayed 12.3 credits
- Wallet scale=6 (micro-units), UNITS_PER_CREDIT=100_000, receive 1.234567 = 1_234_567 minor
  credited_raw = (1_234_567 / 100_000) * 10_000 ≈ 123_456.7 → displayed 12.3457 credits

Ingress/Egress/Storage pricing (defaults):
- ingress_per_gib: 15000 credit units (1.5 credits) per GiB uploaded
- egress_per_gib: 30000 credit units (3.0 credits) per GiB downloaded
- storage_per_gib_month: 10000 credit units (1.0 credit) per GiB per month
```

This avoids floating-point arithmetic entirely.

---

### Wallet & Monetization

- The system is configured with a **single administrator-defined Interledger wallet address** (Phase 5).
- The **native currency of the wallet** is treated as authoritative (USD, BTC, JPY, etc.).
- Pricing is defined **in that currency**, not normalized to USD.
- If exchange rates or wallet currency change, the **administrator must update pricing constants manually**.
- **Early phases**: Credits can be manually added/removed via API for testing.
- **Later phases**: Web Monetization integration for automatic payment.

```text
SYSTEM_WALLET_ADDRESS=https://sandbox.ilp.link/stephanitaly
UNITS_PER_CREDIT = 10  (minor wallet currency units per credit)
```

## Storage Layout

User data is segregated by identity using normalized paths:

```text
users/<userHash>/<uploadID>
```

- `userHash` = SHA256 hex-encoded hash of the user identity.
- `uploadID` = UUID v4 generated by the server.
- The structure intentionally uses user hash for privacy and collision resistance.

### Phase 2-4: Filesystem Storage
- Local filesystem storage in `./data/` directory
- Metadata files (`.info`) track upload state for resumability
- TUS protocol for chunked uploads
- Server proxies all upload/download I/O

### Phase 5+: S3 Storage
- S3-compatible object storage (Hetzner Object Storage)
- Storage path: `s3://h32bb/users/{userHash}/{uploadID}`
- Metadata stored in Redis (no `.info` files)
- Presigned URLs for direct browser ↔ S3 communication
- Server handles auth/accounting only (no I/O proxy)

## Chunking & Accounting

### Chunk Definition

- **Chunk size is fixed at 16 MiB**.
- This chunk definition is used consistently for:
  - ingress charging,
  - egress charging,
  - and storage rounding.

No distinction is made between “transport chunk” and “billing chunk”.

---

### Pricing Constants (Credits)

```text
PER_GB_INGRESS_RATE = 1.0   credits per GiB
PER_GB_EGRESS_RATE  = 8.0   credits per GiB
PER_GB_STORAGE_DAILY_RATE = 0.033 credits per GiB per day
```

All calculations use **GiB (2³⁰ bytes)**.

---

### Charge Formula

For any operation involving `bytes`:

```text
chunks = ceil(bytes / 16MiB)
credits = chunks * (PER_GB_RATE / (GiB / 16MiB))
```

**Phase 2-4 (Per-Chunk Charging):**
- Failed chunks are **not charged**.
- Only successfully completed chunks incur deductions.

**Phase 5+ (Upfront Charging):**
- Full file cost is deducted upfront when presigned URL is generated.
- User is charged even if upload/download fails partway.
- Simpler accounting (no chunk tracking through S3).

---

## Upload Semantics (Ingress)

### Phase 2-4: TUS Protocol with Per-Chunk Charging

- Uploads use the **tus protocol**, intercepted and enforced by the Go backend.
- File size **may be unknown upfront** (tus supports chunked uploads).
- Server proxies all upload I/O and charges per successful chunk.

Rules:
- Uploads are allowed if the user has **at least one ingress chunk worth of credits**.
- Credits are deducted **after each successful chunk** (16 MiB).
- If credits drop below zero during upload:
  - The upload **continues** to completion.
  - The account balance becomes **negative**.
- New uploads are **blocked** when account is frozen (balance < 0).
- Partial uploads are resumable via tus protocol.

### Phase 5+: Presigned S3 URLs with Upfront Charging

- Clients upload directly to S3 using presigned PUT URLs.
- File size **must be known upfront**.
- Server generates presigned URL and deducts full file cost immediately.
- No server proxy for upload I/O (reduced latency, bandwidth, CPU).
- A server proxy path remains available for CSP-constrained environments (e.g., Hetzner S3 without CSP header support).

Rules:
- Uploads are allowed if the user has **sufficient credits for full file cost**.
- Credits are deducted **upfront when presigned URL is generated**.
- If frozen or insufficient balance → request rejected with 402 Payment Required.
- No per-chunk tracking (presigned URL expiry limits abandoned uploads).
- Presigned URLs valid for 1 hour.

---

## Download Semantics (Egress)

### Phase 2-4: Server-Proxied Streaming with Per-Chunk Charging

- File size is determined **before download starts**.
- Server proxies all download I/O.
- Downloads are allowed even if credits will go negative.

Rules:
- Credits are deducted **per successfully streamed chunk** (16 MiB).
- Failed chunks are not charged.
- Downloads may drive the account balance negative.
- Frozen accounts cannot download files (balance < 0).

### Phase 5+: Presigned S3 URLs with Upfront Charging

- Clients download directly from S3 using presigned GET URLs.
- Server generates presigned URL and deducts full file cost immediately.
- No server proxy for download I/O (reduced latency, bandwidth, CPU).

Rules:
- Downloads allowed only if user is **not frozen** (balance >= 0).
- Credits are deducted **upfront when presigned URL is generated** (full file cost).
- If frozen → request rejected with 402 Payment Required.
- No per-chunk tracking.
- Presigned URLs valid for 5 minutes.

## Storage Backend Architecture

### Phase 2-4: Filesystem Storage

**Data Location:**
- Local filesystem in `./data/` directory
- Path: `data/users/{userHash}/{uploadID}`
- Metadata in `.info` files (JSON)

**Server Role:**
- All file I/O proxied through server (upload/download)
- Handles chunking, progress tracking, resumability
- Manages `.info` files for state

### Phase 5+: S3-Compatible Object Storage

**Data Location:**
- Hetzner Object Storage bucket: `h32bb`
- Path: `users/{userHash}/{uploadID}-{filename}` (filename sanitized)
- Metadata stored in S3 object metadata (no Redis dependency)

**S3 Configuration:**
```json
{
  "endpoint": "https://hel1.your-objectstorage.com",
  "region": "hel1",
  "bucket": "h32bb",
  "access_key": "***",
  "secret_key": "***",
  "presigned_url_expiry_upload": 3600,
  "presigned_url_expiry_download": 300
}
```

**Server Role:**
- Generates upload allocations (charges credits) and proxy-uploads file data to S3
- Generates presigned GET URLs for download by resolving the key from `uploadId`
- Verifies cross-user access control

**Security:**
- Bucket is private (no public access)
- Presigned URLs are scoped to exact S3 key
- CORS configured for trusted domains only
- Signature validation prevents tampering

## Storage Charging

- Storage usage is sampled **once per day at 00:00 UTC** (Phase 3+).
- Billing is based on a **snapshot of bytes stored at that moment**.
- Bytes are rounded up to 16MiB chunks before charging.
- Storage charges continue regardless of account balance.
- If storage charge causes balance to go negative, account becomes frozen.

---

## Account States

### Active
- Full read/write access.

### Frozen (Insufficient Credits)
Triggered when the balance is negative after daily storage charging.

Frozen accounts:
- ✅ can log in
- ✅ can list folders and files
- ❌ cannot upload
- ❌ cannot download file contents
- ❌ cannot modify filesystem state

---

## Data Retention & Deletion

- **Activity** is defined as a **successful login**.
- If no activity occurs for **120 consecutive days**:
  - All user data is automatically deleted.
  - The account record may be retained for audit purposes.

No grace period is defined in v1.

---

## File Semantics & Safety

- All uploaded files are treated as **opaque blobs**.
- No server-side extraction, unpacking, or interpretation occurs.
- Symlinks and special files are irrelevant at this stage and not supported.

---

## Developer Requirements

- All components must be designed with **test-driven development**.
- User accounting is accessed via an **interface**:
  - Initial implementation: in-memory.
  - Future implementation: **TigerBeetle**.
- Dev-login and prod auth paths must be clearly separated via build tags.

## Explicit Non-Goals (v1)

- Multi-tenant / shared vaults
- Public or shared links
- Encryption key management
- S3 API compatibility
- Third-party app integration
- Versioning, recycle bins, soft delete

### Phase 5 Scope (Explicitly Out of Scope)

- Resumable uploads via S3 multipart API (deferred to Phase 5.1)
- Multiple S3 buckets or per-user buckets
- AWS-specific features (Glacier, versioning, lifecycle)
- Encryption at rest (S3 bucket encryption is sufficient)
- CDN integration (deferred to Phase 6)
- Migration script for existing filesystem data (fresh start)
- Direct S3 API exposure to clients (presigned URLs only)

---

## Phase 6 Preview: Sharing Links (Planned)

- Each file gets a **Share** button that issues a time-limited link (7 days). Clicking again issues a new 7-day link (old links remain valid until they expire).
- Anonymous users can download via the link **if** the owner has sufficient credits; the owner pays the egress cost after a successful download.
- Expired links are rejected server-side; egress charging happens only on successful download completion.
- Rate limiting and basic abuse controls should be applied to link creation and download redemption.

---

## Final Notes

This design is:
- **cost-predictable**: Upfront charging (Phase 5+) eliminates per-chunk accounting overhead
- **simple to reason about**: Presigned URLs shift I/O complexity to S3
- **scalable**: Direct S3 access removes server as bottleneck
- **tolerant of edge cases**: Frozen accounts, negative balances handled by policy engine
- **well-positioned for future changes**: Crypto, pricing, and backend updates can evolve independently
- **secure by default**: Presigned URLs are time-limited, action-limited, and path-limited
